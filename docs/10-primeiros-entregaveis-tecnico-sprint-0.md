# Primeiros Entregáveis Técnicos — Sprint 0

> Wikilink: [[Primeiros Entregáveis Técnicos — Sprint 0]] · Sprint 0 — Fundação e Alinhamento

Este documento define o que a Sprint 0 vai entregar do lado técnico, com prioridade. Ele não é escopo aberto; é o conjunto mínimo que deixa o projeto preparado para começar a entregar comportamento real na Sprint 1.

---

## 1. Objetivo

Queremos transformar as decisões da Sprint 0 em coisas organizadas que possam ser usadas e revisitadas. O foco não é chegar a uma app completa; é chegar a uma base pronta para o próximo trabalho.

---

## 2. Entregáveis priorizados

### 2.1 P0 — Estrutura de documentação e critério de projeto

Entregáveis:

- [[Convenções de Projeto]]
- [[Critério de Pull Request]]
- [[Qualidade e Usabilidade]]
- [[Primeiros Entregáveis Técnicos — Sprint 0]]
- atualização do [[Cérebro do Projeto]] com os tópicos que estavam “a definir”

Justificativa:

- antes de codar, o time precisa de um lugar onde as escolhas e o critério estejam visíveis
- isso reduz retrabalho e permite que o próximo entregável seja conduzido com mais clareza

---

### 2.2 P1 — Definir os primeiros contornos técnicos

Entregáveis:

- terminar de delimitar os primeiros módulos que serão reais quando o código aparecer
- nomear os primeiros serviços/responsabilidades esperados, em especial:
  - entrada e representação do documento
  - motor de análise/review
  - catálogo de regras base
  - assistência IA como opcional
  - rascunho e estado de revisão
- deixar explícito o que não será feito ainda

Justificativa:

- evita começar a implementar coisas que vão mudar de ideia logo depois
- define onde cada responsabilidade deve viver

---

### 2.3 P2 — Preparar o caminho para os primeiros casos testáveis

Entregáveis:

- começar a pensar em como serão escritos os primeiros testes de regras e de fluxo principal
- definir que tipos de dado serão usados nos testes iniciais
- anotar os primeiros casos que importam e os pontos frágeis observados nos documentos atuais

Justificativa:

- quando o código começar, precisamos de casos reais e não de abstrações vazias
- isso também ajuda a deixar claro que regras e análise serão testadas antes de serem consideradas “prontas”

---

## 3. O que NÃO é entregável desta versão da Sprint 0

- escolha final de stack concreta, se ainda não estiver definida
- motor de regras completo
- serviço de IA real
- app ou interface pronta
- catálogo final de regras

Esses itens continuam atribuídos a Sprints futuras, a partir do momento em que o escopo estiver mais definido.

---

## 4. Ordem sugerida de execução

1. Terminar de organizar a documentação de condução e critério, porque ela serve de base para tudo.
2. Deixar explícito em que módulos o código futuro irá nascer.
3. Anotar os primeiros casos e fragilidades que importam para testes e qualidade.
4. Só então, se daí, passar para o primeiro entregável do código real.

---

## 5. Como julgar se isso foi entregue

Consideramos entregue quando:

- a documentação de condução existir e estiver coerente com o resto do projeto
- os contornos técnicos iniciais estiverem descritos
- os primeiros entregáveis técnicos estiverem listados e priorizados
- o [[Cérebro do Projeto]] refletir o que foi feito e adicionado nesta continuação da Sprint 0
